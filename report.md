## 1. Executive Summary

Nazo is a well-structured anime trivia Android app with **impressive scope**: AI-powered quiz generation, a guessing game mode, daily challenges, survival/blitz/versus modes, achievements, statistics, backup/restore, widgets, onboarding, and a polished Compose UI with custom animations.

**Overall Grade: B+** — The app is feature-rich and largely well-architected, but suffers from:
- **Memory leaks** in large Composable screens
- **Security vulnerabilities** around API key storage
- **Race conditions** in the guessing game prefetch system
- **Missing error boundaries** that can crash the app on malformed AI responses
- **No unit tests or UI tests whatsoever**
- **Giant monolithic files** (NazoApp.kt ~75KB, OnboardingScreen.kt ~71KB, LocalQuestionBank.kt ~339KB) that hurt maintainability

## 2. Critical Bugs & Fixes

### 🔴 BUG-001: `HttpURLConnection` Leak in `ApiClient.kt`
**File:** `data/remote/ApiClient.kt`  
**Severity:** HIGH

```kotlin
// Current code — connection.disconnect() is in finally, BUT:
// If an exception is thrown BEFORE connection.outputStream.use { ... }
// completes, the connection may not be properly closed.
```

**Problem:** `HttpURLConnection` instances can leak sockets if `disconnect()` is called on a connection that was never fully established. On Android, this exhausts the connection pool and causes `UnknownHostException` or `ConnectException` on subsequent calls.

**Fix:**
```kotlin
suspend fun generateQuiz(...): Result<List<Question>> = withContext(Dispatchers.IO) {
    runCatching {
        val connection: HttpURLConnection? = null
        try {
            val endpoint = providerById(providerId)
                ?: throw IllegalArgumentException("Unknown provider: $providerId")
            val url = endpoint.buildUrl(model, apiKey)
            connection = (URL(url).openConnection() as HttpURLConnection).apply {
                requestMethod = "POST"
                doOutput = true
                connectTimeout = 30_000
                readTimeout = 60_000
                endpoint.headers(apiKey).forEach { (k, v) -> setRequestProperty(k, v) }
            }
            // ... rest of logic
        } finally {
            connection?.disconnect()
        }
    }
}
```
**Also applies to:** `fetchModels()`, `GuessApiClient`, `GuessImageFetcher`, `UpdateDownloader`, `UpdateChecker`.

### 🔴 BUG-002: Race Condition in Guessing Game Prefetch (`kickGuessPrefetch`)
**File:** `ui/NazoApp.kt` (lines ~850–950)  
**Severity:** HIGH

**Problem:** `guessPrefetchJob` is assigned inside a coroutine launched by `scope.launch`. If the user rapidly taps "Next Round" multiple times, or quits and starts a new game, the old job may complete AFTER the new game started and write stale state into `guessPhase`.

**Current vulnerable pattern:**
```kotlin
guessPrefetchJob = scope.launch {
    // ... long-running work ...
    guessPhase = GuessPhase.Playing(...) // <-- can overwrite a newer round!
    guessPrefetchJob = null
}
```

**Fix:** Add a generation counter or check `guessRound` before every state mutation:
```kotlin
fun kickGuessPrefetch(startedRound: Int) {
    val targetRound = startedRound + 1
    val job = scope.launch {
        val result = GuessApiClient.generateGuessRound(...)
        // CRITICAL: verify we're still on the expected round
        if (guessRound != startedRound) return@launch
        // ...
        if (guessRound == targetRound) {
            guessPhase = GuessPhase.Playing(...)
        }
    }
    guessPrefetchJob = job
}
```

### 🔴 BUG-003: `LocalQuestionBank.kt` — 339KB Inline Data Crashes on Low-Memory Devices
**File:** `data/LocalQuestionBank.kt`  
**Severity:** HIGH

**Problem:** The entire question bank (~4,000+ questions) is inlined as Kotlin code. This causes:
1. **Dex method count bloat** — each question is a method call in the generated bytecode
2. **Slow cold start** — the class initializer runs ALL question construction on the main thread during class loading
3. **OOM on low-end devices** — the object graph stays in memory forever as a static singleton
4. **No way to update questions without an app release**

**Fix:** Move the bank to a Room database or at minimum a JSON asset file loaded on-demand:
```kotlin
// In assets/questions.json
// Load lazily:
object LocalQuestionBank {
    private var _questions: List<Question>? = null

    fun getQuestions(count: Int, topic: String, difficulty: String): List<Question> {
        if (_questions == null) {
            _questions = loadFromAssets() // or Room query
        }
        return _questions!!.filter { ... }.shuffled().take(count)
    }
}
```

### 🟡 BUG-005: `SessionMemory` Leaks Across Process Death
**File:** `session/SessionMemory.kt`  
**Severity:** MEDIUM

**Problem:** `SessionMemory` uses `mutableSetOf()` and `mutableListOf()` in-memory only. If the app process is killed by the OS (common on low-memory devices), all "seen this session" data is lost, causing question repetition.

**Fix:** Persist to `DataStore` or `SharedPreferences` with a TTL (e.g., 24h):
```kotlin
object SessionMemory {

    // Use DataStore with timestamped entries, prune on read
}
```

### 🟡 BUG-006: `formatElapsed()` Can Return Negative Time
**File:** `ui/NazoApp.kt`  
**Severity:** LOW-MEDIUM

```kotlin
private fun formatElapsed(startedAt: Long): String {
    if (startedAt == 0L) return "0m 0s"
    val secs = ((System.currentTimeMillis() - startedAt) / 1000).toInt().coerceAtLeast(0)
    return "${secs / 60}m ${secs % 60}s"
}
```

**Problem:** If the device clock changes (NTP sync, user changes time), `startedAt` can be in the future, producing negative seconds. The `coerceAtLeast(0)` handles it but the root cause (relying on `System.currentTimeMillis()` for duration) is fragile.

**Fix:** Use `SystemClock.elapsedRealtime()` for all duration measurements:
```kotlin
var quizStartedAtRealtime by remember { mutableLongStateOf(0L) }
// Set: quizStartedAtRealtime = SystemClock.elapsedRealtime()
// Read: val secs = ((SystemClock.elapsedRealtime() - quizStartedAtRealtime) / 1000).toInt()
```

## 3. Security Issues

### 🔴 SEC-001: API Keys Stored in `SharedPreferences` (Even "Encrypted")
**File:** `data/settings/SecureStorage.kt`, `ApiKeyStore.kt`  
**Severity:** CRITICAL

**Problem:** The app stores LLM API keys (Gemini, OpenAI, Anthropic) using what appears to be `EncryptedSharedPreferences` or a custom wrapper. However:
1. `EncryptedSharedPreferences` uses the Android Keystore, which is **hardware-backed only on API 23+ with StrongBox**
2. On emulator or rooted devices, the master key can be extracted
3. Keys are held in memory as plain `String` objects (immutable in JVM, linger in heap until GC)

**Fix:**
- Use **Android Keystore** with `KeyGenParameterSpec` requiring biometric auth for key use
- Store keys as `CharArray` and zero out after use (though `HttpURLConnection` needs `String` for headers, so this is limited)
- **Never** log API keys — audit all `Log.d/e/i` calls in `ApiClient.kt`, `GuessApiClient.kt`
- Consider using a **proxy server** so the app never holds the raw key

---

### 🔴 SEC-002: `GuessImageFetcher` Fetches Images from Arbitrary Wikis Without Sanitization
**File:** `modes/guessing_game/GuessImageFetcher.kt`  
**Severity:** HIGH

**Problem:** The image fetcher constructs URLs from AI-generated entity names and hits Fandom wikis. If the AI returns a malicious entity name with path traversal (`../etc/passwd`) or URL injection, the app could fetch from unexpected hosts.

**Fix:**
```kotlin
// Sanitize and validate the URL
val sanitized = entityName.replace(Regex("[^a-zA-Z0-9_-]"), "_")
val url = "https://$wikiDomain.fandom.com/wiki/$sanitized"
// Validate host
val parsed = Uri.parse(url)
require(parsed.host?.endsWith(".fandom.com") == true)
```

## 4. Performance & Memory

### 🔴 PERF-001: `NazoApp.kt` is 75KB — Monolithic God Composable
**File:** `ui/NazoApp.kt`  
**Severity:** HIGH

**Problem:** This single file contains:
- Navigation state management
- Quiz orchestration (normal, survival, blitz, versus)
- Guessing game orchestration
- Theme/state hoisting for 15+ screens
- Generation request handling
- Daily challenge logic
- Practice deck logic

This violates **single responsibility** and causes:
- Slow compilation (Compose compiler struggles with large files)
- Impossible to unit test
- Merge conflicts on every feature branch
- Recomposition of the entire app when any hoisted state changes

**Fix:** Extract into ViewModels:
```kotlin
// One ViewModel per flow
class QuizViewModel(...)
class GuessingGameViewModel(...)
class HomeViewModel(...)
// NazoApp.kt becomes a thin router:
@Composable fun NazoApp(...) {
    val quizVm: QuizViewModel = viewModel()
    val guessVm: GuessingGameViewModel = viewModel()
    // ...
}
```

## 5. Architecture & Code Quality

### 🔴 ARCH-001: No ViewModels — All Business Logic in Composables
**File:** `ui/NazoApp.kt`, `ui/screens/*.kt`  
**Severity:** HIGH

**Problem:** Every screen receives callbacks and state through parameters. This is the "callback hell" anti-pattern in Compose. State is hoisted to `NazoApp.kt` and drilled down 3–5 levels.

**Impact:**
- Can't write unit tests for business logic
- Can't preview screens in Android Studio (needs 15+ parameters)
- Recomposition cascades through the entire tree

**Fix:** Introduce `ViewModel` from `androidx.lifecycle`:
```kotlin
class QuizViewModel(
    private val apiClient: ApiClient,
    private val statsStore: QuizStatsStore,
) : ViewModel() {
    private val _uiState = MutableStateFlow(QuizUiState())
    val uiState: StateFlow<QuizUiState> = _uiState.asStateFlow()

    fun startQuiz(topic: String, difficulty: String, count: Int) { ... }
    fun answerQuestion(selected: String) { ... }
}
```

---

### 🔴 ARCH-002: `data/settings/` — 10+ Separate Preference Files
**File:** `data/settings/*.kt`  
**Severity:** MEDIUM-HIGH

**Problem:** Each preference (theme, stats, backup, profile, etc.) has its own `DataStore` or `SharedPreferences` file. This causes:
- 10+ disk I/O operations on app start
- Potential data inconsistency (no transactions)
- Hard to migrate or backup atomically

**Fix:** Consolidate into a single `DataStore` with a protobuf schema:
```protobuf
message AppPreferences {
    ThemePreferences theme = 1;
    ProfilePreferences profile = 2;
    QuizStats stats = 3;
    // ...
}
```

### 🟡 ARCH-003: `ApiClient.kt` Mixes HTTP, JSON Parsing, and Business Logic
**File:** `data/remote/ApiClient.kt`  
**Severity:** MEDIUM

**Problem:** The same object handles:
- Raw HTTP (`HttpURLConnection`)
- Provider-specific URL/header construction
- JSON coercion and markdown stripping
- Question parsing and validation

```
remote/
  HttpEngine.kt          // Pure HTTP

```

## 9. Build & CI/CD

### 🟡 CI-001: `build-release.yml` — No Version Code Auto-Increment
**File:** `.github/workflows/build-release.yml`  
**Severity:** LOW

The release workflow likely doesn't auto-increment `versionCode`. This can lead to Play Store rejections if a human forgets to bump it.

**Fix:**
```yaml
- name: Bump version code
  run: |
    VERSION_CODE=$(date +%s)
    sed -i "s/versionCode = [0-9]*/versionCode = $VERSION_CODE/" app/build.gradle.kts
```
